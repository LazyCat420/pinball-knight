## 1. THE BLOCKER — DO THIS FIRST, IT IS ONE COMMAND

`.wslconfig` is **already edited and waiting**. It needs a WSL restart to take
effect, which nobody could run from inside the session that made the change:

    wsl --shutdown          # from PowerShell, not from inside WSL

That applies `memory=32GB` (was 40) and `autoMemoryReclaim=dropcache` (was
`gradual`).

### Why the box could not run Wan

Measured 2026-08-08, host total minus `vmmemWSL`'s working set:

    Windows alone   27.3 GB   chrome 10.8 (40 procs), IDE 5.9, vivaldi 3.9,
                              Obsidian 2.1, + OS
    WSL cap         40   GB   (.wslconfig)
                    -------
    worst case      67.3 GB   RAM guard HARD at 62.5 · physical 63.9

**The cap was larger than the machine.** Any run that filled WSL's allowance had
to cross the ceiling. Guaranteed, not unlucky.

And a Wan run fills it without trying. The two experts are 11.2 GB each, so a
run reads **22.4 GB of GGUF** and Linux caches every byte. `free` reports that
cache as AVAILABLE because it is reclaimable — so nothing inside WSL ever looks
wrong — while Windows counts the balloon as used and the guard stops ComfyUI.
Traced on a real attack clip, sampling every 3s:

    host used     35.32 → 60.65 GB   (+25.3)
    comfy RSS      1.02 → 11.11 GB   (+10.1)
    wsl available 31.28 → 23.50 GB   (-7.8 ONLY)

25 GB of host growth against 10 GB of ComfyUI growth. The gap is page cache.

`.wslconfig` had said `40GB WSL + ~17GB Windows baseline peaks ~57GB`. The
baseline is **27.3 GB**, not 17. `guard.mjs` was retuned for exactly this drift
on 2026-08-05 (its `HOST_SOFT_USED_GB` note measures the same 28.7 GB) and
`.wslconfig` never was. The two disagreed about the machine for three days and
every Wan run paid for it.

⚠️ **32 GB is a function of the Windows baseline, and that baseline grows.** If
the guard starts striking again, re-measure before touching anything:

    host used (Win32_OperatingSystem)  −  (Get-Process vmmemWSL).WorkingSet64

Browsers are 14.65 GB of the current 27.3 — that is the term most likely to move.

### After the restart, verify before trusting it

    powershell.exe -NoProfile -Command "(Get-CimInstance Win32_OperatingSystem) | ForEach-Object { ($_.TotalVisibleMemorySize-$_.FreePhysicalMemory)/1MB }"
    ~/comfy/run.sh -d
    cd src/game/pinball-knight/tools/sprite-forge/comfy
    node cli.mjs animate --init ../work/comfy/create-2026-08-07T20-01-52/create_00001_.png \
                         --preset attack --frames 21 --seed 7 --file-as dog

Expect ~550s and a ghost report printed at the end. If the guard strikes again,
**read `~/comfy/guard.log` first** — the CLI now quotes it for you.

### Optional, and it makes the guard stop killing jobs to reclaim nothing

`guard.mjs`'s SOFT strike now tries to drop the page cache before interrupting,
but it needs one narrow privilege it does not have:

    sudo tee /etc/sudoers.d/bdb-dropcaches <<'EOF'
    lazycat ALL=(root) NOPASSWD: /usr/bin/tee /proc/sys/vm/drop_caches
    EOF
    sudo chmod 0440 /etc/sudoers.d/bdb-dropcaches

Without it the guard logs the reason once and behaves exactly as before. **This
code path has never executed.** It is written and syntax-checked and that is
all — treat it as unverified until you see a `reclaimed NNGiB` line in the log.

## 4. THE PATTERN THIS SESSION KEPT HITTING

Worth naming, because it cost most of the day: **three separate causes wore the
same symptom.** "The render fails and memory is full" was, in order:

1. leaked headless browsers from the playtest harness (9 GB),
2. the panel's runaway poll loop (5.6 GB in one renderer, and it is worst
   *while rendering*, which is what made it look like a generation bug),
3. the WSL cap being larger than the machine.

Each was found only after the previous one was cleared, and each one on its own
looked like the whole answer. If the guard strikes after the restart, assume
there is a fourth thing rather than that the third fix failed.

The other repeated lesson: **every failure in this stack used to be silent.**
`fetch failed`, `execution failed: []`, a toast that erased itself after six
seconds, `state: "done"` with zero frames and exit 0. All four now name their
cause, and that change is worth more than any single fix in this handoff —
three sessions were spent theorising over strings that had the answer in them.
